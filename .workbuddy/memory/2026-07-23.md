## 排查：格子内双击打开应用/文件 慢、无响应（仅分析，未改动）
- 调用链：ItemsView_DoubleTapped(WidgetWindow.Items.cs:139) → OpenItem → ViewModel.OpenItem(WidgetViewModel.Operations.cs:97) → FileService.OpenItem(FileService.cs:1258) → Win32Helper.OpenFile(1126) → OpenFileOrChooseApp(1093) → ShellExecuteW(Win32Helper.cs:431，同步 P/Invoke，在 UI 线程执行)。
- 主因A（双击常"无响应"）：每个条目 Border 设了 CanDrag="True" + DragStarting(WidgetWindow.xaml:86,100)，而打开只挂在 DoubleTapped。WinUI 中 Border 一旦被判定为拖拽手势即取消父级 ListView 的 DoubleTapped，鼠标两次点击间 1~2px 抖动就会触发拖拽、双击永不触发 → 经常无响应（打开默认需双击 DoubleClickToOpen=true）。
- 主因B（等半天打不开/很慢）：整个打开路径在 UI 线程同步执行。ShellExecuteW 本身不等待目标进程，但遇"无文件关联(返回31/27)"会走 SHOpenWithDialog(Win32Helper.cs:1116)、或坏快捷方式走 ResolveBrokenShortcutWithShellUi(FileService.cs:1262)，二者都是模态对话框；owner 传的是 IntPtr.Zero（来自 OpenFile(IntPtr.Zero,…)），对话框可能落在置顶格子背后 → 表现成"卡住等半天"。SmartScreen/MOTW、需提权、网络/可移动盘路径也会在 UI 线程同步阻塞。
- 已排除：图标/缩略图 hydration 已异步分批并用 Task.Run 卸载 Win32 提取(IconHelper.cs:507)，不阻塞 UI 线程；ShellExecuteW 不等待进程退出。
- 次因：ItemsView_DoubleTapped 要求 e.OriginalSource.DataContext is WidgetItem，点在内层子元素时可能静默不打开。

## 结论收敛（用户补充：搜索弹窗里也打不开 → 坐实根因）
- 搜索弹窗 ExecuteItem 对文件调同一个 OpenFileOrChooseApp 且传真实 OwnerWindowHandle(SearchPopupWindow.xaml.cs:108)；格子传 IntPtr.Zero。两条路径唯一差别是 hwnd，但两条都打不开 → 排除 hwnd 为根因；hwnd 只影响后续 SHOpenWithDialog 是否可见，不是决定因素。
- 共同根因：裸 ShellExecuteW + lpDirectory=null + "open" 动词，从 DeskBox.exe(非 shell 宿主) 调用。对 .md 这类 open 动词依赖 shell 宿主激活/打包应用/UserChoice 哈希的文件，legacy ShellExecute 返回 31(无关联)，而 Explorer 作为 shell 宿主会自动修复哈希/用打包激活，故秒开。
- 修复方向：用 System.Diagnostics.Process.Start(UseShellExecute=true)（内部走 ShellExecuteEx，与 Explorer 行为一致）替换裸 ShellExecuteW，设 WorkingDirectory=父目录；格子改传真实 _hWnd；失败捕获 Win32Exception 并给可见提示而非吞返回值；Task.Run 包裹避免 UI 阻塞；保留 ShowInExplorer 回退。代码库已有 Process.Start 先例(QuickCaptureWidgetWindow.Items.cs:112 / Updater)。
- 遗漏的主因C（可复现、特定文件打不开，区别于上面的"间歇无响应"）：Win32Helper.OpenFile 调 ShellExecuteW 时 hwnd=IntPtr.Zero 且 lpDirectory=null（Win32Helper.cs:1095, 1126-1128）。Explorer 用自身 hwnd + 文件所在目录作工作目录。差异在：①对默认程序是 打包/UWP Store 应用 或 UserChoice 哈希损坏的 .md，ShellExecute 直接返回 31(无关联)→ 静默进入 SHOpenWithDialog(IntPtr.Zero)(:1116)，对话框落在置顶格子背后 → 看似"打不开"；Explorer 作为 shell 宿主会自动修复哈希/用打包激活，故秒开。②lpDirectory=null 让目标进程继承 DeskBox 的 CWD；若 DeskBox 为 WS_EX_TOPMOST 且目标非置顶，可能开在格子背后。
- 设计缺陷放大问题：OpenFile 的返回值被 `_ =` 丢弃（OpenFile.cs:1271 / OpenFile 内 1128），FileService.OpenItem 永远返回 OpenedOrHandled，ShellExecute 失败无任何提示/Toast/可见日志 → 用户完全无反馈。

## ★真正的根因（①②③ 之后用户仍反馈打不开，加诊断日志定位）
- 加 [DIAG] 日志在 ItemsView_DoubleTapped / OpenItem / ResultsPanel_DoubleTapped / ExecuteItem / OpenFileOrChooseApp。用户测试后日志显示：格子+搜索两次都 `Process.Start OK`（无异常），但 MarkText 进程随后消失、用户看不到窗口。
- 直接命令行启动 marktext.exe 触发崩溃：`SyntaxError: Invalid or unexpected token` 在 .md 第1行——MarkText(Electron) 把 .md 当 Node 脚本执行了。
- 根因：**`ELECTRON_RUN_AS_NODE=1`** 在 agent bash 环境里（WorkBuddy 是 Electron 宿主）。从 bash 启动 DeskBox → DeskBox 继承该变量 → Process.Start 启动 MarkText(Electron) 也继承 → MarkText 以纯 Node 模式运行 → require(.md) 崩溃退出。Explorer 是系统 shell 无此变量故双击秒开。.md 默认程序=MarkText(ProgId MarkText.Document, 命令 "C:\Program Files\marktext\marktext.exe" "%1")。该变量不在 HKCU/HKLM 持久环境，只在本会话 env。
- ①②③(换 Process.Start)对本案无效——ShellExecuteW 同样继承 env 也会触发；但 ①②③ 仍是合理改进(更现代 API+真实 hwnd+失败可见)，保留。
- 真正修复：Win32Helper.OpenFileOrChooseApp 启动子进程前临时 `Environment.SetEnvironmentVariable("ELECTRON_RUN_AS_NODE", null)`，finally 恢复。UseShellExecute=true 不支持自定义 env block，故用临时改进程环境法。保护所有 Electron 类默认程序(MarkText/VS Code/Obsidian 等)。
- 诊断日志([DIAG])目前仍留在代码里，待确认修复后清理。
- 启动坑补充：本机 marktext 测试时 bash 把 `/d/DeskBox/...` 转义成 `d:\d\DeskBox\...` 误导过排查；测 Windows 程序传路径务必 `MSYS_NO_PATHCONV=1` + Windows 反斜杠路径。
- 注意：OpenItem(item) 单参 [RelayCommand] 仍 void 调 FileService.OpenItem(item) 无 ownerHwnd，未在 XAML 绑定(OpenItemCommand 无引用)；其余 OpenFile(string) 调用方(托盘/设置页/跳转列表，用于 URL/exe/文件夹)行为保持，仅底层换 ShellExecuteEx。
- 未做(用户未要求)：④Task.Run 包裹避免 UI 阻塞；⑤ShowInExplorer 回退提示。
- 另一潜在因子（取决于安装渠道）：若用户装的是 Store/MSIX 版，打包应用的 ShellExecute 行为（令牌/能力）与桌面版不同，可能影响某些 handler 的文档激活。需向用户确认安装渠道。

- 经验：WinUI 里若 UserControl 自己管理 Visibility（靠 Mode/状态机），外层设 `Visibility=Collapsed` 会被其 `Loaded`/`ActualThemeChanged`/`PropertyChanged` 回调覆盖；正确做法是把"隐藏意图"透传进控件自身的可见性开关（如 Mode=Hidden），而非只改外层属性。

## 天气胶囊双层 icon 真正根因（用户 23:16 反馈"还是2个叠着"）
- 上一次改 `CompactTitleIcon.Mode = Hidden` 无效，因为 `WidgetShell.xaml` 里 title icon 的 Mode 走 `Mode="{x:Bind TitleIconMode, Mode=OneWay}"` 绑定到 WidgetShell 的 `TitleIconMode` 依赖属性（全代码从未赋值，恒为默认 `Color`）。直接给 `CompactTitleIcon.Mode` 赋值会被这个 OneWay 绑定在下一轮刷新时**覆盖回 Color**，于是 title icon 又显示、继续和 emoji 叠着。
- 正确修法（`Controls/WidgetShell.xaml.cs` `SetCompactPresentation`）：改设**绑定源** `TitleIconMode = showTitleIcon ? WidgetTitleIconModeNames.Color : WidgetTitleIconModeNames.Hidden;`。`Hidden` 经 x:Bind 传到控件，`WidgetTitleIcon.ApplyVisualState` 在 Mode==Hidden 时 `Visibility=Collapsed` 并 return，且能扛住其自身的 `Loaded`/`ActualThemeChanged` 重显逻辑。
- 验证：dotnet build 0 错误。杀旧 PID 30780 → 重建 → 启动新 PID 32996。
- 经验：XAML 里 `x:Bind OneWay` 绑定的属性，**代码里要改就得改绑定源（ViewModel/owner 的属性），不能直接改绑定目标**，否则会被绑定覆盖。

## 天气胶囊双层 icon —— 完整根因链（用户 23:18 仍反馈"还是2层"）
- 现象：天气胶囊左侧 CompactTitleIcon（默认天气彩色 glyph）+ CompactEmojiIcon（emoji）叠着。
- 根因链（三道关卡，任一道都会让隐藏失效）：
  1. `WidgetTitleIcon` 控件自己管 Visibility：`Mode==Hidden` 才 `Collapse` 并 return，否则 `Loaded`/`ActualThemeChanged`/属性变更时会把自身重新 `Visible`。所以单纯设外层 `Visibility=Collapsed` 没用。
  2. **第一版修法**（直接 `CompactTitleIcon.Mode=Hidden`）失败：XAML 里 `Mode="{x:Bind TitleIconMode, Mode=OneWay}"` 绑到 WidgetShell 的 `TitleIconMode` DP（默认 Color），OneWay 绑定会把我直接赋的 `Hidden` 覆盖回 Color。
  3. **第二版修法**（改绑定源 `this.TitleIconMode=Hidden`）仍失败：`ContentWidgetWindow.xaml.cs:566` 的 `ContentWidgetShell.TitleIconMode = SettingsService.Settings.WidgetTitleIconMode;` 在每次外观/主题刷新时把该 DP **无脑重置成全局图标模式**（通常 Color），于是 `Hidden` 又被冲掉，glyph 重新叠在 emoji 上。
- **最终修法（彻底解耦）**：
  1. `WidgetShell.xaml` 去掉 CompactTitleIcon 上的 `Mode="{x:Bind TitleIconMode...}"` 绑定。
  2. `WidgetShell.xaml.cs` `SetCompactPresentation` 内**直接**设 `CompactTitleIcon.Mode`：有 emoji（`hasEmoji`）→ `WidgetTitleIconModeNames.Hidden`（彻底收起，且扛得住控件自身重显）；否则 → 用户全局图标模式（`App.Current.SettingsService.Settings.WidgetTitleIconMode`，空保护回落 `Color`）。
  3. 去掉绑定后，`ContentWidgetWindow:566` 那行对 `ContentWidgetShell.TitleIconMode` 的赋值变成无副作用（CompactTitleIcon 不再读它），再也无法覆盖 emoji 隐藏逻辑。
- 验证：dotnet build 0 错误。杀旧 PID 32996 → 重建 → 启动新 PID 29648。
- 经验**：当"全局外观刷新"会重置某个 DP/属性、而该属性又被 XAML 绑定喂给某个控件时，最稳的做法是让真正需要精细控制的那个控件**脱离该绑定、改由业务方法直接赋值**，从而避免被刷新逻辑覆盖。

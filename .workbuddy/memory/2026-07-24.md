## 微信聊天文件拖拽修复（第九轮，根因定位）
- **根因**：`WidgetWindow.NativeDragDrop.cs` 的 `InstallFileDropSubclass` 调用 `RegisterDragDrop` 注册原生 IDropTarget 到 HWND，**覆盖了 WinUI 3 的内部 IDropTarget**。当微信聊天文件以 `FileDrop`（CF_HDROP）格式拖入时：①原生 handler 的 `Drop` 方法被调用，但 WinUI 包装的 COM IDataObject 与原生 COM 接口不兼容 → `TryExtractFilePaths` 抛 COM 异常 → .NET COM 互操作层吞掉异常 → `App.Log` 不执行 → `pdwEffect` 默认 0（NONE）→ drop 被静默消费；②XAML 的 `RootGrid_Drop` 永远不会被触发。微信图片（Chromium 格式，含 `FileContents,FileGroupDescriptorW` + URL）走的是不同路径（URL 下载），不受影响。
- **日志铁证**：`[DropTarget] Registered IDropTarget` 注册成功（×多个窗口），但 `NativeDrop received` **从未出现**（COM 异常吞掉了日志之前的代码）。XAML `RootDragOver accepted=Move` 正常触发，但 `RootGrid_Drop` **从不触发**（对于 FileDrop 格式）。
- **修法**：移除 `InstallFileDropSubclass` 中的 `RegisterDragDrop` 调用和原生 IDropTarget 创建。保留 WM_DROPFILES 子类（旧式拖放的后备路径）。注释说明移除原因。卸载逻辑中的 null check 自动安全。
- `WidgetWindow.Stacks.cs` 用户自己改了 `PointerRoutedEventHandler` → `PointerRoutedEventArgs`、`PointerPressedEvent` → `UIElement.PointerPressedEvent`（编译错误修复）。
- `WidgetWindow.ItemDragOut.cs` 用户自己调整了 URL fallback 的位置（StorageItems 失败后立即尝试 URL，不等最后）。
- **最终方案**：移除 RegisterDragDrop 后发现 XAML Drop 仍然不触发（WinUI 3 AllowDrop 对微信 FileDrop 格式的 OLE 兼容性 bug）。采用 **DragOver 中检测鼠标松手**的 workaround：在 `RootGrid_DragOver` 中用 `Win32Helper.IsKeyDown(0x01)` 检测鼠标左键状态，当检测到松手且 `_pendingDropDataView` 非空时，直接调用 `GetDropPathsAsync` + `ViewModel.ImportPathsAsync` 处理拖放数据。`_pendingDropDataView` 在 DragOver 中设置、DragLeave/Drop 中清除。
